# workbuddy-sync

在多台机器之间**双向同步** WorkBuddy 的个人资产。

## 它解决什么问题

WorkBuddy 的数据默认只存在本机（`~/.workbuddy`）。两台机器同时用就会出现**数据分叉**：
家里新建的技能公司看不到，公司跑的自动化家里看不到，对话记录各存各的。
本工具把这些资产通过一个共享目录（网盘）双向合并，让多台机器最终收敛到同一份数据。

## 与官方「迁移助手」类技能的区别

| | 官方迁移技能 | 本技能 |
|---|---|---|
| 场景 | **一次性搬家**（旧机 → 新机） | **长期双向同步**（两台机器都要继续用） |
| 传输 | zip 包（微信/U盘） | 共享目录（网盘自动同步） |
| 频率 | 搬一次就结束 | 每天/每次开机自动 |

两者互补。如果用户是"换新电脑、旧机不要了"，用迁移技能更合适；
如果用户是"两台机器长期都要用"，用本技能。

## 关键概念（先跟用户对齐）

| 概念 | 说明 |
|---|---|
| **同步目录** | 一个两台机器都能访问的共享文件夹。OneDrive / 坚果云 / 百度网盘 / 局域网共享都行，**必须是双向同步型网盘**（不能是只能上传的） |
| **机器标识** | 每台机器一个稳定短 ID（首次运行自动生成），用来区分「谁写的包」 |
| **包** | 每台机器把自己全部资产打包成 `state/from-<标识>.zip`，**只写自己的包**，永不覆盖对方的。2.3.0 起再叠「增量包」：只含相对上次变化的文件（`state/deltas/`），pull 时自动叠加到基线上 |
| **合并** | 拉取时把对方的包合并进本机：数据库按主键去重追加，追加型日志（对话记录）做行级并集 |

**⚠️ 三条铁律（必须在开始前告诉用户）**

1. `push` 可以在 WorkBuddy 运行时执行（只读快照，安全）
2. `pull` 会写数据库，**执行前必须完全退出 WorkBuddy**（含托盘图标）
3. **同一时间只让一台机器 push**，否则两边同时改同一文件会产生冲突副本

## 准备 · 拿到引擎

`wb-sync` 命令与技能包里的 `wb_sync.py` 是**同一套逻辑的两种入口**，任选其一：

| 方式 | 适合 | 怎么用 |
|---|---|---|
| **技能包自带**（推荐） | 双机长期同步 | 直接用包里的 `python wb_sync.py <动作>`，代码在共享盘里只有一份 |
| **GitHub Release 的 wheel** | 想要 `wb-sync` 命令 | `pip install <Release 里的 .whl>` |
| **PyPI**（即将上线） | — | `pip install workbuddy-sync` |

> 找不到 Python？WorkBuddy 自带一个，路径形如
> `%USERPROFILE%\.workbuddy\binaries\python\versions\<版本>\python.exe`。
> 便携模式也可以直接双击 `pull.cmd` / `push.cmd`，脚本会自己去找。

下文统一用 `wb-sync <动作>` 表示，等价于便携模式的 `python wb_sync.py <动作>`。

## 执行流程

### 第 0 步 · 前置检查

```
wb-sync doctor
```

会检查：WorkBuddy 目录、数据库可读性、进程占用、同步目录是否可写、以及
**是否有不在白名单里的新资产**（客户端升级后会新增目录，这是"静默漏同步"的根源）。

> 也可以直接 `wb-sync ui` 打开本地面板，让用户自己在界面上点 `doctor` / `push` / `pull`
> —— 适合不想敲命令的用户。面板只监听 `127.0.0.1`，默认端口 8765
> （`wb-sync ui --port 9000` 可改）。

### 第 1 步 · 确定同步目录

问用户用哪个网盘，然后二选一：

- **自动探测**：如果用的是 OneDrive，`wb-sync` 会自动找到它，无需配置
- **手动指定**：其他网盘 / 自定义位置，创建 `<配置目录>\config.json`：

```json
{ "sync_root": "D:\\Cloud\\wb-sync" }
```

`<配置目录>` 在 Windows 上是 `%LOCALAPPDATA%\wb-sync`。

> ⚠️ 提醒用户：该文件夹若在网盘里显示为「仅在线」占位符，要右键设为
> **「始终保留在此设备上」**，否则读取会失败。

### 第 2 步 · 首次 push（第一台机器）

确认 WorkBuddy 可以开着，然后：

```
wb-sync push
```

首次运行会打印「本次同步范围」（要传什么、排除什么），这是**有意设计的隐私告知**，
应当让用户看一眼并确认。

### 第 3 步 · 第二台机器 pull

1. 等网盘把这个目录同步下来
2. **完全退出 WorkBuddy**
3. 执行 `wb-sync pull`
4. 重新打开 WorkBuddy —— 对话、任务、空间就都在了
5. 再执行一次 `wb-sync push`，把这台机器上的数据也推回去

### 第 4 步 · 设为自动（可选，推荐）

长期使用建议做成自动化，避免每天手动敲命令：

- **开机自动拉取**：把 WorkBuddy 的开机自启项从 `WorkBuddy.exe` 改成先 pull 再启动的启动器
  （这样 pull 永远落在"WorkBuddy 还没启动、数据库空闲"的安全窗口里）
- **定时自动推送**：任务计划程序里每天固定时间跑 `push`（push 不锁库，可以随时跑）

具体脚本随发行包提供（`wb-launch.cmd` / `install-autostart.cmd`）。

## 常用命令

```
wb-sync ui             # 打开本地 Web 面板（可视化操作，适合非技术用户）
wb-sync doctor         # 环境自检（先跑这个）
wb-sync where          # 看当前生效的配置与清单来源
wb-sync status         # 看两侧差异，不动文件；含冲突数与增量 seq
wb-sync push           # 本机 -> 同步目录
wb-sync pull           # 同步目录 -> 本机
wb-sync push --dry-run # 预演，只打印计划（含敏感内容体检）
wb-sync push --fail-on-secret  # 严格模式：扫到凭据就中止，不生成包（退出码 2）
```

工作目录里的 `wb_sync.py` 是等效入口（`python wb_sync.py push`），
适用于不便 pip 安装的便携场景。

## 安全边界（必须主动告知用户）

同步的是**个人敏感数据**，包括对话记录、记忆文件、技能（可能含 API Key）。
工具内置的隐私默认值：

- 路径含 `secret` / `credential` / `password` / `token` / `apikey` / `cookie`
  / `auth-state` 等字样的文件**不同步**
- `.key` / `.pem` / `.env` / `.db` 等后缀默认排除
- `auth/` 目录（各类登录态）整体排除
- 单文件超过 200MB 跳过（防视频/模型混入）

**但排除规则不可能覆盖所有情况。** 首次 push 前应提示用户：把 `wb-sync doctor`
打印的同步范围与排除规则看一遍，确认没有不应该上传的东西。

**内容级体检（2.4.0 起）**：上面这些规则都只看**路径名**。凭据常待在名字正常的
文件里（例如 `cli-env/wecom-cli.sh` 的 `agt1-` 令牌），路径层面看不出异常。
push / `--dry-run` / doctor 会对「即将进包的内容」跑凭据规则，命中输出
「文件:行号 + 规则 + 打码值」，**默认只告警不阻断**。

- 要严格把关：`--fail-on-secret`（退出码 2，不生成任何包）
- 确需同步某个带凭据的文件：清单加 `"secret_allow": ["cli-env/*"]`
- 报告与包内 `manifest.json` 的 `secrets` 字段只记规则名与路径，**不含明文**
- 它**不是**加密或脱敏工具，只是一道「让你知道自己在传什么」的闸门

**面板**只监听 `127.0.0.1`，并校验 `Host` 与 `Origin`：浏览器里其他网页无法偷偷
触发 `push` / `pull`（非本机来源一律 403）。命令行工具不受影响。

## 常见问题

| 现象 | 原因与处理 |
|---|---|
| `pull` 提示「请先完全退出 WorkBuddy」 | 进程检测到 WorkBuddy 在运行。彻底退出（含托盘）后重试；确认已退出可加 `--force` |
| `[!] 未能确定同步目录` | 没探测到 OneDrive 且没有 config.json。按第 1 步创建 config.json |
| 两台机器都改了同一个文件 | 会生成 `<文件名>.conflict-<机器>-<时间戳>`，对方版本胜出，本机版本留档。不会丢数据，但需要人工看一眼。台账记在 `<配置目录>\conflicts.json`，`status` 显示「待处理冲突 N 个」；**删掉备份文件，计数自动归零** |
| `push` 提示「包未变化，沿用现有包」 | **不是失败**。内容指纹（路径 + 大小 + mtime + 数据库）与上次相同，就不重写整包，省掉网盘重复上传数百 MB。要强制重建加 `--force` |
| `push` 只写了 `state/deltas/d-xxx.zip`，`from-<机器>.zip` 没动 | 正常。只打包变过的文件，pull 时自动叠加到基线。基线在增量满 24 个、或累计体积赶上基线、或 `--force` 时重建 |
| `pull` 提示「增量包 xxx 尚未同步到本机」 | 同步盘还没传完。已跳过该对端且**不标记已拉取**，等传完再跑一次即可。**不能让基线当成全量合并**，那会拿到过期内容 |
| 只改了一个文件，push 却仍走全量 | 三种可能：对端引擎低于 2.3.0（安全阀自动退回全量）；增量已满 24 个；这次是选择性推送。都属正常 |
| `pull` 提示「数据库尚未合并，本次不标记为已拉取」 | WorkBuddy 没完全退出，DB 被跳过。**退出后重跑一次 `pull`** 即可补齐。刻意不标记，否则下次会因签名相同被永久跳过 |
| 报「共享目录身份不一致」 | 本机指向的目录和之前不是同一个（换盘符 / 网盘改名 / 账号不同）。核对 `sync_root`；确认无误要重新认领，删掉 `<配置目录>\cluster-id` 再重试 |
| `doctor` 提示「有 N 个目录不在同步白名单里」 | **重要**：可能是 WorkBuddy 升级新增了资产目录。核对内容后，需要同步就加进 `<配置目录>\manifest.json` 的 `sync_dirs` |
| `push` 打印「⚠ 敏感内容体检 发现 N 处」 | 包里确实有疑似凭据（显示为打码值）。默认仅告警、包照常生成；要挡住加 `--fail-on-secret`。确需同步该文件就在清单里 `"secret_allow": ["cli-env/*"]` 豁免，**不要**整体关掉扫描 |
| 换了新网盘 / 改了同步目录 | 改 `config.json` 的 `sync_root`，然后重新 push。注意包是**全量**的，会重新上传一次 |
| 电脑重装 WorkBuddy 后不再自动同步 | 重装会把自启项重置回 `WorkBuddy.exe`，重跑一次自启安装脚本即可 |
| 空间列表里有打不开的空壳（路径指向别的机器） | v2.3.0 之前合并进去的记录不会自动改写。跑 `tools/repair_paths.py`：默认只读打印计划，`--apply` 才写库且写前自动备份；工作区根搬过盘的加 `--map "旧根=新根"`。**先干跑再执行** |
| `pull` 报「路径编码 v1 高于本机支持」 | 对端引擎比本机新。该格式**不能被强制读取**（读错等于把占位符当路径写进库）。升级本机后再拉 |
| `doctor` 报「路径编码 本机库有占位符残留」 | 上一次拉取没做完本地化。重新 `pull` 一次；持续出现说明该对端包有问题 |
| 面板端口在听、浏览器却一直转圈 | 用 `pythonw.exe` 启动会出现：无控制台时 handler 无法输出日志，请求走不到收尾。**改用 `python.exe`**；后台自启再加 `WB_SYNC_NO_BROWSER=1` 跳过自动开浏览器 |

## 白名单是数据，不是代码

同步范围写在 `default-manifest.json` 里，不在 Python 代码里。好处：
WorkBuddy 客户端升级新增资产时，**改 JSON 就能跟上，不必改代码**。

三级来源（后者覆盖前者）：

1. 包内 `default-manifest.json` —— 随版本发布的默认值
2. `<配置目录>\manifest.json` —— 用户自己的**追加**（列表取并集，只能加、不能减）
3. 命令行 `--manifest-dir` / 环境变量 `WB_SYNC_MANIFEST_DIR` —— 临时指定

> 想做「减法」（例如某个文件被敏感词误伤、需要放行）只能改**包内**那份，
> 因为用户清单只会取并集。注意升级会覆盖包内清单，需要重做一次。

**给用户的自定义建议**：不要改包内那份（升级会被覆盖），
要加目录就写 `<配置目录>\manifest.json`：

```json
{
  "sync_dirs": ["my-custom-assets"],
  "extra_globs": ["*/large-but-unneeded/*"],
  "secret_allow": ["cli-env/*"]
}
```

`secret_allow` 是「明知里面有凭据但要同步」的豁免（glob）；
`"secret_scan": false` 是整体关闭内容级体检（不推荐，会连以后新增的泄漏一起放过）。
